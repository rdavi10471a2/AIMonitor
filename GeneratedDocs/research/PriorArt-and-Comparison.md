# Prior art: code→architecture doc generators, and how this one differs

> **Authored research, not a generated artifact** (2026-06-09). The files in [`../`](../Architecture.aim.md) and [`../components/`](../components/README.md) are machine-generated by `tools/SelfDocGen`. *This* document is a hand-written survey of comparable tools and an honest comparison against that generator's approach. Sources are linked at the bottom; claims about external tools are from their docs/repos as of mid-2026 and may drift.

## What "our approach" is (the thing being compared)

`SelfDocGen` drives the real `AIMonitor.McpServer.dll` over stdio against AIMonitor's own semantic self-index and emits Markdown + Mermaid. Its defining choices:

1. **Two evidence tiers, never blended.** The *skeleton* (project DAG + topological ranks) is `source-verified` — the compiler-enforced csproj `ProjectReference` graph. The *coupling weights* are `caller/index-verified` — counts of real reference sites pulled from the index.
2. **Coupling = reference-site counts**, not import edges and not estimates. An edge `App → Data | 87 refs` means 87 indexed reference sites in `App` resolve to public symbols in `Data`.
3. **Declared-vs-actual reconciliation.** Every declared `ProjectReference` is checked against live references; declared-but-zero-reference edges are flagged as *candidate-dead* (explicitly **not** proven-dead).
4. **No LLM in the generation path** → deterministic, same index ⇒ byte-identical output.
5. **Epistemic honesty as a first-class section.** Public-surface-only, reference-site semantics, candidate-dead caveats are stated in every doc.

## The landscape (six families of prior art)

| Family | Representative tools | Structure source | Coupling evidence | LLM? |
|---|---|---|---|---|
| **.NET dependency analyzers** | NDepend, ReferenceTrimmer | declared + compiler | afferent/efferent coupling, used-assembly refs | no |
| **Import/AST graphers** | dependency-cruiser, Madge, dep-tree, arkit, emerge, pyreverse | inferred from imports/AST | import/include edges | no |
| **Semantic code-graph indexers** | Sourcetrail, Glean, CodeQL, SCIP/LSIF | indexed facts (defs/refs/calls) | cross-reference facts | no |
| **Architecture-as-code** | C4 model + Structurizr, PlantUML | hand-authored model (DSL) | modeled, not measured | no (DSL) |
| **Architecture fitness functions** | ArchUnit, NetArchTest, ArchUnitNET, import-linter | declared rules over compiled types | pass/fail assertions | no |
| **LLM documentation generators** | DeepWiki, CodeBoarding, Swark, CIAO, ArchAgent | LLM inference (+ some static analysis) | LLM-inferred | yes |

The generator sits at an unusual intersection: it reads a **semantic index** (family 3) but renders an **opinionated architecture doc** (families 4/6) using **declared-vs-actual coupling** (family 1), **deterministically** (unlike family 6).

## Family-by-family comparison

### 1. .NET dependency analyzers — the closest analogs

**NDepend** computes afferent coupling (Ca, who depends on me) and efferent coupling (Ce, who I depend on) for assemblies/namespaces/types, plus derived metrics: Instability `I = Ce/(Ce+Ca)`, Abstractness, and the "zone of pain / zone of uselessness" placement. It renders a dependency graph and a dependency-structure matrix.
- **Overlap:** Ca/Ce *is* directional coupling counting, like our inbound/outbound ref weights.
- **They do more:** a full metrics suite (instability/abstractness), DSM, type/method granularity, cycle detection — we have none of these.
- **We do differently:** we split *declared* (csproj) from *live* and call out the gap; NDepend reports coupling but doesn't frame "declared yet unreferenced" as a finding. We're free, in-repo, diffable Markdown; NDepend is a commercial GUI/CI product.

**ReferenceTrimmer** is the single closest tool to our *dead-edge finding*. It's an MSBuild task + Roslyn analyzer that uses `GetUsedAssemblyReferences` (and an experimental symbol-based mode) to flag declared `ProjectReference`/`PackageReference` items that aren't actually used (warning `RT0002` for project refs).
- **They are more correct on this one axis:** `GetUsedAssemblyReferences` catches *structural/compiler* use (e.g. a base type, an attribute, an assembly-level use) that our **public-surface reference-site** count misses — which is exactly why we label our zeros *candidate*-dead, not dead. ReferenceTrimmer would resolve several of our six "declared-only" edges definitively.
- **We do differently:** ReferenceTrimmer answers one yes/no question (is this ref used?); it produces no architecture narrative, ranks, or coupling weights. **Borrowable:** wire `GetUsedAssemblyReferences` in to *promote* candidate-dead → confirmed-dead.

### 2. Import/AST graphers — same picture, weaker evidence

dependency-cruiser (JS), Madge (JS), dep-tree, arkit (JS/TS/Vue), emerge (multi-language), and pyreverse (Python) parse source and draw module/file dependency graphs, exporting SVG/PNG/PlantUML/Mermaid.
- **They do differently (and worse for our purpose):** edges are *imports/includes*, not resolved reference sites. An unused `import` still draws an edge; an import used 200 times and one used once look identical (no weights). They're language-scoped to their parser.
- **We do differently:** our edges are weighted by resolved reference count from a compiler-grade index, and we reconcile against the declared build graph. dependency-cruiser *can* enforce rules (see family 5), which we don't.

### 3. Semantic code-graph indexers — our substrate, not our output

Sourcetrail (archived) indexed C/C++/Java/Python into a graph DB and offered interactive symbol/reference/dependency exploration. Meta's **Glean** stores typed, schema-defined facts (definitions, references, types, call relationships, inheritance, imports) produced by per-language indexers (plus LSIF/SCIP for Go/Java/Rust/TS). CodeQL exposes code as a queryable database for analysis.
- **Relationship:** AIMonitor's index *is* a tool in this family — its `find_indexed_references` is the "find references" primitive Glean/Sourcetrail expose. The difference is **what we build on top**: these tools give you a graph/query surface and stop; `SelfDocGen` consumes that surface to *author a layered architecture document with a point of view*.
- **Borrowable:** Glean's typed-fact schema (inheritance, call relationships) is richer than what we render — our `relationshipCount = 7` finding is essentially "we under-use the relationship facts the index already has."

### 4. Architecture-as-code (C4 / Structurizr) — opposite direction of truth

Structurizr renders C4 diagrams from a hand-written DSL model; its pitch is that an "as code" model lives in version control, is diffable, and resists drift. Recent work auto-extracts components (e.g. Spring annotations) or uses an agent to scan code into a Structurizr workspace.
- **Same value we get:** diffable, version-controlled, text-defined diagrams.
- **Opposite epistemics:** Structurizr's model is *intended* architecture (what a human asserts); ours is *observed* architecture (what the index proves). C4 separates content from presentation and supports multiple curated views; we emit one fixed view derived from evidence. The honest framing: C4 documents intent and can lie if the code drifts; we document reality and can't show intent the code doesn't yet exhibit. The doc's "Tier *names* are not graph-derived — they are maintained intent" line is exactly the C4-style assertion layered on top of measured structure.

### 5. Architecture fitness functions — enforce vs. describe

ArchUnit (Java), ArchUnitNET / NetArchTest (.NET), and dependency-cruiser rules let you assert "package X must not depend on Y" as unit tests that **break the build** on violation.
- **Different posture:** these are *gates* (pass/fail, prescriptive); `SelfDocGen` is a *mirror* (descriptive, surfaces candidates for human judgement). That matches AIMonitor's broader stance — a hard floor for safety, but a human eyeball for review-level judgements rather than an automated verdict.
- **Borrowable:** the six candidate-dead edges are a ready-made fitness-function backlog — "Indexing must not declare an unused MSBuild ref" could become a NetArchTest assertion once ReferenceTrimmer confirms it's truly dead.

### 6. LLM documentation generators — our sharpest contrast

DeepWiki (Cognition) generates interactive wikis for public GitHub repos at scale; CodeBoarding combines static analysis with LLM reasoning for architecture diagrams + component docs in IDE/CI; Swark turns code into Mermaid via an LLM in VS Code; CIAO and ArchAgent are research systems for LLM-driven architecture documentation/recovery.
- **The contrast that matters:** these infer architecture with an LLM, so they can **hallucinate structure**. Research on LLM-generated documentation found "Diagram Errors" the single most frequent limitation category (32 occurrences in one study), and practitioners report architectural hallucinations being "uniquely expensive" — a wrong code snippet wastes minutes, a wrong *architecture* wastes weeks. Mitigations converge on retrieval/grounding (RAG).
- **Where we win:** every number in our docs is a reference-site count from a compiler-grade index — there is nothing to hallucinate, and re-running yields byte-identical output. We are, in effect, the maximally-grounded end of the RAG spectrum: the "retrieval" is an exact index query and there is no generative step.
- **Where they win:** prose. They explain *why* a component exists, summarize responsibilities, and write onboarding narrative; we emit evidence and a few templated findings. The strongest design is hybrid — our verified structure as the grounded context, an LLM for the prose — with the verified numbers as guardrails the prose may not contradict.

## Honest scorecard

**Where this generator genuinely leads**
- **Grounded by construction.** Reference-site counts from a compiler-grade index — the property the entire LLM-doc family is fighting to retrofit via RAG. Re-runs are byte-identical.
- **Declared-vs-live as a first-class signal.** Most graphers show *a* graph; we show the gap between the build's declared graph and the references that actually exist, and we're disciplined about calling it *candidate*-dead.
- **Self-honest.** A standing "Evidence & caveats" section. Almost no comparable tool publishes its own blind spots inline.
- **Zero infrastructure.** No GUI license (NDepend), no hosted service (DeepWiki), no DSL to maintain (Structurizr) — Markdown + Mermaid in the repo.

**Where it's behind (and what to borrow)**
- **Public-surface-only undercounts.** We miss `internal`+`InternalsVisibleTo`, DI registration, reflection, and structural/compiler use. **Borrow** ReferenceTrimmer's `GetUsedAssemblyReferences` to promote candidate-dead → confirmed-dead.
- **csproj skeleton is hardcoded** in `CsprojEdges`, not parsed from the projects. NDepend and ReferenceTrimmer read the real build graph; we transcribe it. **Borrow:** derive the DAG from MSBuild evaluation (AIMonitor already loads MSBuild project truth).
- **No metric suite, no cycle/DSM view** (NDepend), **no temporal/behavioral coupling** from VCS history (CodeScene-style), **no interactive exploration** (Sourcetrail/emerge).
- **Thin prose.** Findings are templated. The hybrid play — verified structure + LLM narrative, numbers as guardrails — is the obvious next step and the one place the LLM family clearly outclasses us.
- **Relationship facts under-used.** `relationshipCount = 7` is partly *our* gap: the index (like Glean) carries inheritance/call facts we don't render.

## Borrowable roadmap (concrete)
1. **Confirm dead edges:** add a `GetUsedAssemblyReferences` pass to split *candidate-dead* from *confirmed-dead*.
2. **Auto-derive the skeleton** from MSBuild evaluation instead of the hardcoded `CsprojEdges` dict.
3. **Surface relationship facts** (inheritance/implements/calls) the index already holds — directly answers the `relationshipCount` finding.
4. **Optional hybrid prose layer:** feed the verified doc to an LLM for narrative, asserting the measured numbers as non-negotiable context (RAG done right).
5. **Add a cycle / instability view** (cheap given we already have the directed graph).
